# Mod Bug Tracking Workflow

> - **Applies to:** Jak 1 / Jak 2 / Jak 3 — all mod branches
> - **Origin:** `master-dev`
> - **Related Guide:** [`github_workflows.md`](github_workflows.md)

> ### Summary
>
> [1. The Form](#1-the-form) · [2. Auto-Labeling](#2-automatic-labeling) · [3. Fix Loop](#3-closing-the-loop-fix--commit--release) · [4. Auto-Sync](#4-automated-syncing-from-releases-the-backend) · [5. Manual Overrides](#5-manual-overrides--debugging)

---

Custom mods get bug reports through a dedicated GitHub Issue Form instead of free-form
issues, so every report carries the structured data needed to reproduce it and to track
the fix through to the next release.

## 1. The form

[`.github/ISSUE_TEMPLATE/mod-bug-report.yml`](../../../.github/ISSUE_TEMPLATE/mod-bug-report.yml)
is offered as **"🧩 Mod Bug Report"** in the issue chooser (alongside **"💡 Mod Suggestion"**). It asks for:

| Field | Why |
| :--- | :--- |
| **Game** | Jak 1 / 2 / 3 — becomes the `jak1`/`jak2`/`jak3` label. |
| **Mod Concerned** | Dropdown listing only mods with **at least one published GitHub Release** — checked live against the Releases API, never against a branch's committed `index.json` (that file can carry a real-looking checksummed version even when no release was ever actually published: a local/dry run, a release later deleted, ...). Shown by the exact display name from that release's notes, not the branch name. Unreleased/beta mods and anything not listed fall to "Other" + a free-text field. Becomes the `mod:<slug>` label. |
| **Mod Version** | The Launcher's displayed version tag, or `git rev-parse HEAD` for a self-built debug copy — pins the exact code the reporter played. |
| **How did you install this mod?** | OpenGOAL Launcher vs. self-compiled debug build — most "works for me" mismatches trace back to this. |
| **Describe the Bug** / **Steps to Reproduce** | Standard bug report fields. |
| **Attachments** | A textarea, so the reporter can drag & drop a screenshot, GIF or video straight into GitHub's uploader — the most useful evidence for gameplay/visual bugs. |
| **Environment Information** | Optional CPU/GPU/OS/OpenGOAL version, or the Launcher's Support Package. |

## 2. Automatic labeling

[`.github/workflows/mod-bug-triage.yml`](../../../.github/workflows/mod-bug-triage.yml)
runs on every issue opened with the `mod-bug` label (the form sets it automatically) and
parses the **Game** and **Mod Concerned** answers to add:

- a game label (`jak1` / `jak2` / `jak3` — the same labels the vanilla templates use), and
- a `mod:<slug>` label derived from the mod's **display name** (e.g. `Peaceful Haven City
  (Freedom Fighters)` → `mod:peaceful-haven-city-freedom-fighters`).

This gives a live queue per mod: `is:issue is:open label:mod:transport-ag-traffic`. Both
labels are created automatically the first time they're needed — nothing to pre-provision.

## 3. Closing the loop: fix → commit → release

1. Fix the bug on the mod's own branch (`jak2/features/transport-ag/traffic`, etc.), same
   as any other change on that branch.
2. Reference the issue in the fix commit or its PR: `Fixes #123` (or `Closes #123`). Once
   that commit lands on the branch, GitHub closes the issue automatically and the issue
   thread keeps a permanent link to the exact commit that fixed it — that's the audit
   trail this workflow exists for.
3. When you cut the next release with `release.yml` (see
   [`mod_distribution_guide.md`](mod_distribution_guide.md)), mention the fixed issue
   number(s) in the `mod_description` or in the GitHub release notes, e.g. `Fixes #123,
   #128`. Players and maintainers can then see at a glance which reported bugs a given
   version tag actually resolves.

## 4. The dropdown keeps itself current — from Releases, not from `index.json`

The **Mod Concerned** options sit between two marker comments in the YAML
(`# BEGIN GENERATED ... / # END GENERATED`) and are regenerated by
[`scripts/modding/sync_bug_report_options.py`](../../../scripts/modding/sync_bug_report_options.py),
never edited by hand. The script:

1. Calls the GitHub Releases API for the repo and drops drafts (pre-releases still count —
   they're genuinely published, just marked experimental).
2. Reads each release's own notes, which `update_mod_catalog.py --generate-release-notes`
   always writes as `## 🎮 <Display Name> — <tag>` with a cover-image URL under
   `jak<N>/<category>/<branch>/...` — that's where the display name, the game, and the
   branch come from. A release whose notes don't match this shape (not produced by this
   project's own release pipeline) is skipped with a warning rather than guessed at.
3. Deduplicates per branch, keeping each mod's most recently published release — so a mod
   renamed between v1.0.0 and v1.1.0 shows its current name, not a stale one.

This is deliberately **not** driven by a branch's committed `index.json`: that file can
show a real-looking checksummed version even when no GitHub Release actually exists for it
(a local `update_mod_catalog.py` run never pushed as a release, a release that was later
deleted, ...). Only an actual Release is proof a player can download the mod, so it's the
only signal this list trusts.

- **Automatic:** [`.github/workflows/mod-bug-report-sync.yml`](../../../.github/workflows/mod-bug-report-sync.yml)
  runs the script on every `release` event (published/edited/unpublished/deleted) and
  commits the refreshed dropdown straight to `master-dev` if it changed.
- **Manual:** `task modding-sync-bug-report-options` (add `-- --dry-run` to preview without
  writing).
- Retired mods and renames disappear/update on their own at the next release event — there
  is no line to remove by hand. "Other" always covers whatever hasn't been released yet.
