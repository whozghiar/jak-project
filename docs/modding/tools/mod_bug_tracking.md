# 🇬🇧 English Version

Custom mods get bug reports through a dedicated GitHub Issue Form instead of free-form
issues, so every report carries the structured data needed to reproduce it and to track
the fix through to the next release.

## 1. The form

[`.github/ISSUE_TEMPLATE/mod-bug-report.yml`](../../../.github/ISSUE_TEMPLATE/mod-bug-report.yml)
is offered as **"🧩 Mod Bug Report"** in the issue chooser (alongside **"💡 Mod Suggestion"**). It asks for:

| Field | Why |
| :--- | :--- |
| **Game** | Jak 1 / 2 / 3 — becomes the `jak1`/`jak2`/`jak3` label. |
| **Mod Concerned** | Dropdown listing only mods with **at least one published GitHub Release** — checked live against the Releases API, never against a branch's committed `index.json` (that file can carry a real-looking checksummed version even when no release was ever actually published: a local/dry run, a release later deleted, ...). Shown by the exact display name from that release's notes, not the branch name. Unreleased/beta mods and anything not listed fall to "Other" + a free-text field. Becomes the `mod:<slug>` label. |
| **Mod Version** | The Launcher's displayed version tag, or `git rev-parse HEAD` for a self-built debug copy — pins the exact code the reporter played. |
| **How did you install this mod?** | OpenGOAL Launcher vs. self-compiled debug build — most "works for me" mismatches trace back to this. |
| **Describe the Bug** / **Steps to Reproduce** | Standard bug report fields. |
| **Attachments** | A textarea, so the reporter can drag & drop a screenshot, GIF or video straight into GitHub's uploader — the most useful evidence for gameplay/visual bugs. |
| **Environment Information** | Optional CPU/GPU/OS/OpenGOAL version, or the Launcher's Support Package. |

## 2. Automatic labeling

[`.github/workflows/mod-bug-triage.yml`](../../../.github/workflows/mod-bug-triage.yml)
runs on every issue opened with the `mod-bug` label (the form sets it automatically) and
parses the **Game** and **Mod Concerned** answers to add:

- a game label (`jak1` / `jak2` / `jak3` — the same labels the vanilla templates use), and
- a `mod:<slug>` label derived from the mod's **display name** (e.g. `Peaceful Haven City
  (Freedom Fighters)` → `mod:peaceful-haven-city-freedom-fighters`).

This gives a live queue per mod: `is:issue is:open label:mod:transport-ag-traffic`. Both
labels are created automatically the first time they're needed — nothing to pre-provision.

## 3. Closing the loop: fix → commit → release

1. Fix the bug on the mod's own branch (`jak2/features/transport-ag/traffic`, etc.), same
   as any other change on that branch.
2. Reference the issue in the fix commit or its PR: `Fixes #123` (or `Closes #123`). Once
   that commit lands on the branch, GitHub closes the issue automatically and the issue
   thread keeps a permanent link to the exact commit that fixed it — that's the audit
   trail this workflow exists for.
3. When you cut the next release with `release.yml` (see
   [`mod_distribution_guide.md`](mod_distribution_guide.md)), mention the fixed issue
   number(s) in the `mod_description` or in the GitHub release notes, e.g. `Fixes #123,
   #128`. Players and maintainers can then see at a glance which reported bugs a given
   version tag actually resolves.

## 4. The dropdown keeps itself current — from Releases, not from `index.json`

The **Mod Concerned** options sit between two marker comments in the YAML
(`# BEGIN GENERATED ... / # END GENERATED`) and are regenerated by
[`scripts/modding/sync_bug_report_options.py`](../../../scripts/modding/sync_bug_report_options.py),
never edited by hand. The script:

1. Calls the GitHub Releases API for the repo and drops drafts (pre-releases still count —
   they're genuinely published, just marked experimental).
2. Reads each release's own notes, which `update_mod_catalog.py --generate-release-notes`
   always writes as `## 🎮 <Display Name> — <tag>` with a cover-image URL under
   `jak<N>/<category>/<branch>/...` — that's where the display name, the game, and the
   branch come from. A release whose notes don't match this shape (not produced by this
   project's own release pipeline) is skipped with a warning rather than guessed at.
3. Deduplicates per branch, keeping each mod's most recently published release — so a mod
   renamed between v1.0.0 and v1.1.0 shows its current name, not a stale one.

This is deliberately **not** driven by a branch's committed `index.json`: that file can
show a real-looking checksummed version even when no GitHub Release actually exists for it
(a local `update_mod_catalog.py` run never pushed as a release, a release that was later
deleted, ...). Only an actual Release is proof a player can download the mod, so it's the
only signal this list trusts.

- **Automatic:** [`.github/workflows/mod-bug-report-sync.yml`](../../../.github/workflows/mod-bug-report-sync.yml)
  runs the script on every `release` event (published/edited/unpublished/deleted) and
  commits the refreshed dropdown straight to `master-dev` if it changed.
- **Manual:** `task modding-sync-bug-report-options` (add `-- --dry-run` to preview without
  writing).
- Retired mods and renames disappear/update on their own at the next release event — there
  is no line to remove by hand. "Other" always covers whatever hasn't been released yet.

# 🇫🇷 Version Française

Les bugs de mods passent par un formulaire GitHub Issue dédié plutôt que par une issue
libre, afin que chaque rapport contienne les données structurées nécessaires pour le
reproduire et pour suivre le correctif jusqu'à la prochaine release.

## 1. Le formulaire

[`.github/ISSUE_TEMPLATE/mod-bug-report.yml`](../../../.github/ISSUE_TEMPLATE/mod-bug-report.yml)
apparaît comme **« 🧩 Mod Bug Report »** dans le sélecteur d'issue (aux côtés de **« 💡 Mod Suggestion »**). Il demande :

| Champ | Pourquoi |
| :--- | :--- |
| **Game** | Jak 1 / 2 / 3 — devient le label `jak1`/`jak2`/`jak3`. |
| **Mod Concerned** | Liste déroulante des mods ayant **au moins une GitHub Release publiée** — vérifié en direct via l'API des Releases, jamais via le `index.json` committé sur une branche (ce fichier peut afficher une version avec un checksum qui a l'air réel même si aucune release n'a jamais été réellement publiée : un run local/à blanc, une release supprimée par la suite, ...). Affiché avec le nom d'affichage exact tiré des notes de cette release, pas le nom de la branche. Les mods non encore publiés/en beta et tout ce qui n'est pas listé tombent sur « Other » + un champ libre. Devient le label `mod:<slug>`. |
| **Mod Version** | Le tag de version affiché par le Launcher, ou `git rev-parse HEAD` pour une build debug auto-compilée — fixe précisément le code joué par le rapporteur. |
| **How did you install this mod?** | Launcher OpenGOAL vs. build debug auto-compilée — la plupart des « ça marche chez moi » viennent de là. |
| **Describe the Bug** / **Steps to Reproduce** | Champs standards de rapport de bug. |
| **Attachments** | Une zone de texte permettant de glisser-déposer directement une capture, un GIF ou une vidéo dans l'uploader de GitHub — la preuve la plus utile pour un bug visuel/gameplay. |
| **Environment Information** | CPU/GPU/OS/version OpenGOAL optionnels, ou le Support Package du Launcher. |

## 2. Étiquetage automatique

[`.github/workflows/mod-bug-triage.yml`](../../../.github/workflows/mod-bug-triage.yml)
se déclenche sur chaque issue ouverte avec le label `mod-bug` (posé automatiquement par le
formulaire) et analyse les réponses **Game** et **Mod Concerned** pour ajouter :

- un label de jeu (`jak1` / `jak2` / `jak3` — les mêmes labels que les modèles vanilla), et
- un label `mod:<slug>` dérivé du **nom d'affichage** du mod (ex. `Peaceful Haven City
  (Freedom Fighters)` → `mod:peaceful-haven-city-freedom-fighters`).

Cela donne une file d'attente en direct par mod : `is:issue is:open label:mod:transport-ag-traffic`.
Les deux labels sont créés automatiquement dès leur première utilisation — rien à
provisionner à l'avance.

## 3. Boucler la boucle : correctif → commit → release

1. Corrigez le bug sur la branche du mod concerné (`jak2/features/transport-ag/traffic`, etc.),
   comme tout autre changement sur cette branche.
2. Référencez l'issue dans le commit de correction ou sa PR : `Fixes #123` (ou `Closes #123`).
   Une fois ce commit posé sur la branche, GitHub ferme l'issue automatiquement et le fil de
   l'issue garde un lien permanent vers le commit exact qui l'a corrigée — c'est exactement
   la trace d'audit que ce flux vise à fournir.
3. Lors de la prochaine release via `release.yml` (voir
   [`mod_distribution_guide.md`](mod_distribution_guide.md)), mentionnez le(s) numéro(s)
   d'issue corrigé(s) dans `mod_description` ou dans les notes de release GitHub, ex.
   `Fixes #123, #128`. Joueurs et mainteneurs voient ainsi immédiatement quels bugs
   rapportés un tag de version donné résout réellement.

## 4. La liste déroulante se maintient seule — à partir des Releases, pas du `index.json`

Les options de **Mod Concerned** se trouvent entre deux commentaires-marqueurs dans le YAML
(`# BEGIN GENERATED ... / # END GENERATED`) et sont régénérées par
[`scripts/modding/sync_bug_report_options.py`](../../../scripts/modding/sync_bug_report_options.py),
jamais éditées à la main. Le script :

1. Appelle l'API GitHub Releases du dépôt et écarte les brouillons (drafts) — les
   pré-releases comptent, elles sont bel et bien publiées, juste marquées expérimentales.
2. Lit les notes de chaque release, que `update_mod_catalog.py --generate-release-notes`
   écrit toujours sous la forme `## 🎮 <Nom d'affichage> — <tag>` avec une URL d'image de
   couverture sous `jak<N>/<catégorie>/<branche>/...` — c'est de là que viennent le nom
   d'affichage, le jeu et la branche. Une release dont les notes ne correspondent pas à ce
   format (pas produite par le pipeline de release du projet) est ignorée avec un
   avertissement plutôt que devinée.
3. Déduplique par branche en gardant la release la plus récemment publiée de chaque mod —
   un mod renommé entre la v1.0.0 et la v1.1.0 affiche donc son nom actuel, pas un ancien.

Ce mécanisme repose délibérément **sur autre chose que** le `index.json` committé d'une
branche : ce fichier peut afficher une version avec un checksum qui a l'air réel même si
aucune GitHub Release n'existe réellement pour elle (un run local d'`update_mod_catalog.py`
jamais poussé en release, une release supprimée par la suite, ...). Seule une vraie Release
prouve qu'un joueur peut télécharger le mod ; c'est donc le seul signal auquel cette liste
fait confiance.

- **Automatique :** [`.github/workflows/mod-bug-report-sync.yml`](../../../.github/workflows/mod-bug-report-sync.yml)
  exécute le script à chaque évènement `release` (publiée/éditée/dépubliée/supprimée) et
  commit la liste rafraîchie directement sur `master-dev` si elle a changé.
- **Manuel :** `task modding-sync-bug-report-options` (ajoutez `-- --dry-run` pour prévisualiser
  sans écrire).
- Les mods retirés ou renommés disparaissent/se mettent à jour tout seuls au prochain
  évènement de release — il n'y a aucune ligne à retirer à la main. « Other » couvre
  toujours ce qui n'a pas encore été publié.
